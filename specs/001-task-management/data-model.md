# Phase 1 Data Model: Task Management

## Entity: Task

Represents a single item on the shared task list.

| Field | Type | Constraints | Notes |
|-------|------|-------------|-------|
| `id` | integer (or UUID) | Primary key, generated by the database | Stable identifier used in URLs (`/api/tasks/{id}`) |
| `title` | text | Required; non-empty after trimming whitespace; max length 200 characters, enforced at the API layer | FR-001, FR-002 |
| `description` | text | Optional (nullable / defaults to empty string); max length 2000 characters, enforced at the API layer | FR-001 |
| `archived` | boolean | Required; defaults to `false` on creation | FR-005–FR-007, FR-013 |
| `created_at` | timestamp (UTC) | Required; set once at creation; immutable thereafter | FR-010 |
| `updated_at` | timestamp (UTC) | Required; set at creation; updated whenever `title`, `description`, or `archived` changes | FR-011 |

No relationships to other entities — `Task` is standalone, and there is no `User`/owner relationship in this feature (FR-012).

### Validation Rules

- `title` must be non-blank (reject empty string or whitespace-only) on both create and edit (FR-002).
- `title` MUST be at most 200 characters and `description` MUST be at most 2000 characters; a create or edit request exceeding either limit MUST be rejected with a 422 response (FR-002; spec.md Edge Cases — "unreasonably long title or description").
- A request to edit, archive, unarchive, or delete a `Task` whose `id` does not exist MUST return "not found" rather than silently succeeding or creating a record (FR-014).

### State Transitions

```
[created] --(archive)--> [archived]
[archived] --(unarchive)--> [active]
[active] --(archive)--> [archived]      (setting archived=true while already true is a no-op, FR-013)
[archived] --(unarchive)--> [active]    (setting archived=false while already false is a no-op, FR-013)
[active | archived] --(delete)--> [gone, irreversible]
```

- `title`/`description` edits are orthogonal to the archived/active state and are allowed in either state (User Story 2, Acceptance Scenario 3).
- A no-op archive/unarchive transition does **not** advance `updated_at` (FR-013); an actual state change does.
- Deletion is terminal: once deleted, the row is removed and the `id` cannot be reused to retrieve it again (FR-008, FR-009).
